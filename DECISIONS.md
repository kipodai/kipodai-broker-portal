# Decisions Log

Ambiguous product/implementation choices, and why. Newest at bottom.

## Phase 0 — Scaffold

- **Package manager / bundler:** Vite + React, `react-router-dom` for the 4 routes (`/login`, `/`, `/archive`, `/admin/upload`, `/report/:week`). Spec didn't mandate a router; chosen because it's the standard fit for a small multi-page SPA and keeps route/role checks readable.
- **API path convention:** frontend calls `/api/*`, redirected via `netlify.toml` to `/.netlify/functions/*`. Keeps frontend fetch calls stable if the functions runtime ever moves (e.g. Cloudflare fallback).
- **Anthropic / Resend calls via raw `fetch`, not SDKs:** both APIs are simple enough over HTTP that adding `@anthropic-ai/sdk` and `resend` as dependencies wasn't worth it. Netlify Functions run on Node 18+, which has global `fetch`. Reduces dependency surface and makes the "optional key → fallback" branching easy to read in one file.
- **Session auth via HMAC-signed cookie, no library:** Node's built-in `crypto` module covers this; spec explicitly asked to keep auth lightweight and not build OAuth.
- **Shared pure logic lives in `server/`, not `netlify/functions/`:** `server/parser.js` and `server/metrics.js` are pure modules with no Netlify runtime dependency, so Vitest can import and test them directly against `/fixtures` without spinning up functions. `netlify/functions/*.js` are thin HTTP wrappers that call into `server/`.

## Phase 1 — Parser

- **Real fixture filenames don't match the spec's exact substrings.** The actual ABI Studio exports in `/fixtures` are named `Mamma Chia_Weekly Trends_...`, `Mamma Chia_Trend Analysis_...`, `Mamma Chia_Geo Performance By State Data Selection Table_...` — spaces, not underscores. The spec anticipated this ("fall back to header-row detection if names change"), so `classifyByFilename` tries the exact substring first and `classifyByHeaderContent` (anchor-cell match on `WM Week` / `Week` / `State`) is the real-world path for all three sample files. This is exercised directly in `tests/parser.test.js` ("filename drift falls back to header detection").
- **Header row search is bounded to the first 5 rows.** Prevents a stray data cell that happens to equal an anchor string from being misread as a header row, while still tolerating the known 0-row and 1-row preambles.
- **All non-week/non-State columns coerced to number-or-null**, never left as raw strings — this is what makes "blank LY → null, never 0" hold uniformly across File A/B/C without per-column special-casing.
- **Geo_Performance parses by header name for every column except `State`**, since the spec says the column set "may include more" — only `State` is a hard requirement; anything else present is carried through as a coerced number.

## Phase 2 — Metrics engine

- **All vs-LY percentages are recomputed from raw TY/LY dollar figures**, not read from ABI Studio's own pre-computed `%Chg vs LY` columns. Keeps L1W and L4W (summed) comparisons using the identical formula (`(ty-ly)/ly`) instead of mixing a per-row provided value for L1W with a self-computed one for L4W.
- **U/S/W momentum uses `U/S/W (Valid Store)`**, not the `(POS Stores)` variant — chosen for consistency with the store-count gap metric, which is explicitly framed as Valid Store Count vs POS Store Count.
- **"Momentum negative two periods running"** is implemented as: L4W-vs-P4W negative AND P4W-vs-(P4W-prior) negative — i.e. two consecutive period-over-period comparisons, requiring 12 weeks of history. With fewer than 12 weeks, the flag simply can't fire (treated as `null`/false, not an error).
- **Supply-driven correlation thresholds:** instock < 95% (the existing flag threshold) and POS $ decline ≤ -15% vs LY, both within the most recent 13 weeks, with a non-empty week-overlap between the two sets. -15% sits between the -10% plain decline-flag threshold and the sample's actual -22% to -34% dip, specifically so a POS-only decline (no instock drop) doesn't accidentally satisfy the correlation on its own — verified by both a real-fixture test and a synthetic false-positive test.
- **OTIF alerting beyond the literal Alert Rules list:** the spec's Alert Rules section only names "OTIF In Full % < 95% (flag)", but the Metrics Engine section separately describes "flag either < 95% in L1W or a ≥3-point drop vs prior week" for File B generally. Implemented as: `otif_in_full_flag` (flag, In Full only, matching the canonical list) plus two additional `watch`-severity alerts for a ≥3-point single-week drop in either On Time % or In Full %. No standalone "On Time % < 95%" flag exists since it isn't in the canonical Alert Rules list.
- **Geography $500 floor applies to both growth and decline rankings**, applied identically — a state can't appear in "fastest growing" or "declining" without first clearing the floor, but the Top 5 by raw POS $ ranking ignores the floor entirely (a top-5 state is definitionally well above it in practice).

## Phase 4 — Auth / Storage / Functions

- **Netlify Functions v2 (Web `Request`/`Response`) used throughout**, not the classic `(event, context)` handler shape — chosen so `upload.js` can use `req.formData()` natively for the 3-file multipart upload instead of manually decoding a base64 body.
- **`server/auth.js` takes a raw cookie-header string, not the framework's request object**, decoupling session logic from the Netlify runtime shape entirely — this is what makes `tests/auth.test.js` able to unit-test cookie verification and `requireRole()` without any HTTP mocking.
- **Password comparison uses `crypto.timingSafeEqual`** via `safeStringEqual()`, not `===`, since two long-lived shared passwords are exactly the kind of low-traffic, high-value secret where a timing side-channel is worth closing for near-zero cost.
- **`Secure` cookie attribute is conditional on host** (`isLocalHost` check) rather than always-on, so local `netlify dev` over plain HTTP on `localhost` still receives the session cookie in the browser.
- **Upload flow is stateless preview→publish**, not a two-step "upload then confirm from server memory": the frontend resubmits the same 3 files with `mode=publish` after the admin reviews the `mode=preview` response. Simpler than holding parsed-but-unpublished state server-side, at the cost of re-parsing the files once more on publish — an acceptable trade for weekly-cadence file sizes.
- **Re-publishing a week preserves `sendLog`** (carried forward from the existing stored report, if any) — overwriting a report's numbers on a corrected re-upload should not erase the record of who it was already emailed to.
- **`/api/session` is a deliberately unauthenticated-safe, role-revealing endpoint** used only to drive frontend UI (which nav links/buttons to show). It is explicitly not a trust boundary — every admin-only function independently calls `requireRole()` regardless of what this endpoint reports, so a compromised or bypassed frontend can't grant itself admin UI access to real actions.

## Phase 5 — Narrative / Email

- **Anthropic and Resend called via raw `fetch`**, no SDK dependency (see Phase 0 decision above) — `generateNarrative()` catches any failure (network, non-2xx, empty text) and falls back to the deterministic template rather than propagating the error, so a flaky/misconfigured key degrades gracefully instead of blocking report generation.
- **Narrative template mirrors the Anthropic prompt's rules** (lead with the POS $ vs LY fact, explicit supply-driven callout when that alert key is present, otherwise fall through to other flag messages) so the two code paths produce comparably-shaped summaries even though only one calls out to Claude.
- **Email chart is a hand-built inline SVG polyline**, not a rendered chart image — avoids a server-side headless-browser/canvas dependency entirely; only POS $ TY vs LY is drawn (not Instock %, unlike the portal's dual-axis chart) to keep the email digest simple, per spec ("Keep the email to: exec summary, KPI table, alerts, link").
- **`send-email.js` re-validates recipients against `CLIENT_EMAIL_RECIPIENTS` server-side**, rejecting any address not on that list even if a direct API call bypasses the frontend's checkbox-only UI — this is the same "must never allow free-text recipients, ever, in any future feature" rule from `CLAUDE.md`, enforced at the one place that actually sends mail.

## Post-Phase-2 review findings (fixed)

An adversarial review subagent (see REVIEW LOOP) surfaced two real issues, both fixed:

- **Grand Total matching was case-sensitive** (`server/parser.js`, `parseGeoPerformance`): `row.State.startsWith('Grand Total')` would let a differently-cased export (`"grand total (us)"`) leak into state rankings uncaught. Fixed to `state.toLowerCase().startsWith('grand total')`. Regression test added in `tests/parser.test.js`.
- **The correlation-alert test hardcoded the spec's illustrative week range (202610–202612) as if it were guaranteed to be the active trigger.** It happened to still pass, but for a different reason than it claimed: the real fixture's `currentWeek` is 202628, so the correlation engine's trailing-13-week window is 202616–202628, and the actual overlap that fires the alert is weeks 202616–202619 — a separate, more recent supply dip. The 202610–202612 event described in the spec is real (verified independently) but by the time this fixture's "current week" reached 202628, that dip was 16+ weeks in the past and outside the window on purpose (a resolved issue from months ago shouldn't drive this week's supply-vs-demand callout). Since `/fixtures` gets regenerated weekly per `WEEKLY_RUNBOOK.md` and "current week" always advances, **any test that hardcodes specific week numbers against live fixtures will eventually go stale.** Fixed by splitting into two tests: one pins the historical 202610–202612 data-shape facts (pure regression check, independent of alert logic), the other computes the *expected* trailing-13-week overlap directly from the parsed data using the same threshold logic as `server/metrics.js`, then asserts the alert's `weeks` field matches — no hardcoded week numbers. The `supply_driven_correlation` alert object now also exposes a `weeks` array (previously the overlap was computed internally but never surfaced), which is what made this fix possible and may also be useful for the report UI later (e.g. highlighting the specific weeks on the chart).
- **Minor scope-gap additions**, also from the same review: added an `otif_on_time_watch` alert (On Time % < 95%, watch severity) mirroring the existing In Full % flag — the spec's Metrics Engine section describes both metrics symmetrically even though the canonical Alert Rules list only names In Full explicitly. Added `replInstockPct` to `instock.series13w` alongside `instockPct`, since the spec's Instock bullet names both metrics together.

## Post-launch feature: admin-editable email recipient list

- **`server/recipients.js` is the single shared resolver** (`getEffectiveRecipients()`) for "what addresses is the admin allowed to send to" — used by both `netlify/functions/email-config.js` (what the Send dialog offers) and `netlify/functions/send-email.js` (what it actually accepts on send). Having two independent implementations of this check was the exact failure mode to avoid, since a future edit to one and not the other would silently reopen the "no free-text recipients" hole `CLAUDE.md` explicitly protects.
- **Resolution order: Blobs-stored list wins once one has ever been saved; `CLIENT_EMAIL_RECIPIENTS` env var is only the initial seed.** There's no "revert to env var" button — once an admin saves any edit via `/admin/settings`, the env var is permanently superseded for that deployment. This matches the spec note in `CLAUDE.md` ("if the list moves from env var to Blobs-backed store...").
- **Emails are normalized (trimmed, lowercased, deduped) at write time**, not at read/validation time — `normalizeRecipients()` runs once in the PUT handler before saving. This means the stored list, what `email-config.js` returns to the UI, and what `send-email.js` validates against are always already-normalized strings; the frontend never needs to normalize anything itself, and a case-varied or padded duplicate can't sneak into the stored list.
- **`/admin/settings` is a new admin-only route/page**, gated the same way as `/admin/upload` (client-side `ProtectedRoute adminOnly` redirect + independent server-side `requireRole` check in `recipients.js` — the redirect is convenience only, never the actual boundary).

## Post-Phase-5 review finding (fixed)

A third adversarial review subagent, reviewing `server/narrative.js`/`server/email.js` against the real fixtures, found a real correctness bug directly caused by the trailing-13-week correlation window decision above: **the template narrative said "This decline lines up with a drop in in-stock availability..." unconditionally whenever the `supply_driven_correlation` alert fired — even though that alert can fire from a dip several weeks in the past while the current week (L1W) has since fully recovered.** Reproduced live against the real fixtures: L1W POS $ was *up* 61.4% vs LY (the dip was weeks 202616–202619, now outside the current week), yet the generated narrative read "This week's sales were up 61.4%... **This decline** lines up with a drop in in-stock..." — directly self-contradictory, and exactly the kind of non-analyst-misleading text the REPORT SPEC's narrative rules are meant to prevent.

Fixed in `server/narrative.js`: the template now checks whether L1W itself is declining (`kpi.l1wPosDollarsChgVsLY < 0`) or the correlation alert's `weeks` array includes the current week before using "this decline" language; otherwise it describes the dip as a recent-but-resolved event ("affected sales in prior weeks... though sales have since recovered"). The Anthropic prompt was also tightened with an explicit instruction covering the same distinction, since the LLM path receives the same `weeks`/`currentWeek` fields and could make the identical mistake. Regression tests added in `tests/narrative.test.js`, including the exact real-fixture scenario (up 61.4%, alert weeks not including current week).

## Post-deploy: branding

- **`BROKER_NAME` changed from the placeholder `"Kipod AI"` to the real value `"Shift Retail Group"`.** This had been flagged as an open question in an earlier session (the admin password `shiftretail2026!` was the tell). Left unresolved, the report footer read "Prepared by Kipod AI" directly above "Powered by Kipod AI" (added when the Kipod AI hedgehog logo was added to the footer) — reading as a confusing duplicate even though the two lines mean different things. Resolved by setting `BROKER_NAME` to the actual broker name; "Powered by Kipod AI" (with logo) stays as the tool-vendor credit line, distinct from "Prepared by Shift Retail Group" (the broker whose report this is, matching the spec's footer rule for the client-facing report).
- **Kipod AI logo** lives at `logos/kipodai.png` (not under `src/assets/`) — kept in a top-level `logos/` folder since a second logo (Shift Retail Group's, not yet supplied) is expected to join it there. Imported directly via relative path from `ReportView.jsx`; Vite bundles it fine from outside `src/`.
- Deployed to production at `shiftretailgroup.kipodai.com` (custom domain, CNAME to `kipodai-broker-portal.netlify.app`) — see README deploy section. Netlify's project-level "Secure Site" (`sso_login`) had to be turned off for the app's own password auth to be reachable by non-Netlify-account visitors (it was on by default for new sites on this team/plan).
